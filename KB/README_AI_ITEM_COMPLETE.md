## Введение и концепция

### Что такое AI Item?

**AI Item** — это ключевая концепция в проекте AIAN Vector, представляющая **логическую сущность** (элемент искусственного интеллекта), которая связывается с чанками документов. Это попытка создать **структурированную систему категоризации** кодовых объектов и знаний.

### Основная идея проекта

Основная идея заключалась в создании **иерархической системы знаний** с автоматической категоризацией:

1. **Автоматическое извлечение именованных объектов** из кода (функции, классы, таблицы SQL)
2. **Многоуровневая система чанков**:
   - `0-исходник` — базовые чанки из исходного кода
   - `1-связи` — связи между объектами  
   - `2-логика` — логические выводы и анализ

3. **Контекстная группировка** через `context_code`
4. **Автоматическое связывание** — при векторизации чанка уровня 0 с `full_name` автоматически создается AI Item

## Техническая реализация

### Архитектура системы

```sql
-- Структура таблицы ai_item
CREATE TABLE ai_item (
    id SERIAL PRIMARY KEY,
    full_name TEXT NOT NULL,           -- Полное имя объекта
    context_code TEXT DEFAULT 'DEFAULT', -- Код контекста
    type TEXT,                         -- Тип объекта (function, class, table)
    s_name TEXT,                       -- Короткое имя
    h_name TEXT,                       -- Человеко-понятное имя
    file_id INT REFERENCES files(id),  -- Связь с файлом
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ
);
```

**Уникальность:** `full_name` + `context_code`

### Специализированные парсеры

**Файл:** `packages/core/textSplitters.js`

#### JavaScript/TypeScript сплиттер: `splitJsByObjects()`
- Извлекает: функции, методы, классы, интерфейсы, переменные, импорты/экспорты
- Опции: `includeComments`, `parseImports`
- Определяет `full_name`, `s_name`, `h_name` для каждого объекта

#### SQL сплиттер: `splitSqlByObjects()`
- Извлекает: таблицы, функции, процедуры, views, materialized views, triggers, indexes, sequences, types, domains, schemas, roles, grants
- Определяет имена со схемой (например: `public.users`)
- Для функций включает сигнатуру

#### Markdown сплиттер: `splitMarkdownBySections()`
- Разбивает по заголовкам указанных уровней
- Сохраняет иерархию заголовков (`parent_heading`)
- Определяет `s_name` (краткое имя секции), `h_name` (полное имя с иерархией)

## Архитектура базы данных

### Связь между таблицами

```sql
-- Таблица ai_item - основная сущность
CREATE TABLE public.ai_item (
  id serial PRIMARY KEY,
  full_name text NOT NULL,              -- Полное имя объекта
  context_code text NOT NULL DEFAULT 'DEFAULT',
  file_id int REFERENCES files(id) ON DELETE SET NULL,
  type text,                             -- function, class, table, etc.
  s_name text,                           -- Короткое имя
  h_name text,                           -- Человеко-читаемое имя
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

-- Таблица chunk_vector - чанки с векторизацией
CREATE TABLE public.chunk_vector (
  id serial PRIMARY KEY,
  file_id int REFERENCES files(id) ON DELETE CASCADE,
  ai_item_id int REFERENCES ai_item(id) ON DELETE SET NULL,  -- Связь с AI Item
  parent_chunk_id int REFERENCES chunk_vector(id) ON DELETE CASCADE,
  chunk_content text NOT NULL,
  embedding vector,                      -- Вектор размерности 1536
  chunk_index int,
  type text DEFAULT 'текст',
  level text DEFAULT '0-исходник',       -- 0-исходник | 1-связи | 2-логика
  s_name text,
  h_name text,
  full_name text,
  created_at timestamptz DEFAULT now()
);
```

### Иерархия чанков
- L0 чанк: `parent_chunk_id = NULL`, `level = '0-исходник'`
- L1 чанк: `parent_chunk_id = {L0.id}`, `level = '1-связи'`  
- L2 чанк: `parent_chunk_id = {L0.id}`, `level = '2-логика'`

Все чанки одного AI Item связаны через `ai_item_id`.

## API для работы с AI Items

В системе добавлены следующие API-маршруты:

- `GET /ai-items` - Получение списка всех ai_item
- `GET /ai-item/:id` - Получение информации о конкретном ai_item
- `POST /ai-item/:id/update-context` - Обновление контекста ai_item
- `GET /ai-item/:id/chunks` - Получение всех чанков, связанных с ai_item
- `POST /ai-items/cleanup` - Очистка неиспользуемых ai_item
- `POST /api/ai/ai-item/:id/generate-chunk` - Генерация L1/L2 чанков

## Процесс создания и обновления

### Механизм автоматического создания

**Файл:** `packages/core/DbService.js`, метод `saveChunkVector()`, строки 226-314

```javascript
// Если это чанк уровня 0 и у него есть full_name, создаем или связываем с ai_item
if (level === '0-исходник' && full_name) {
  console.log(`[DB] Создание AI Item для чанка с full_name: "${full_name}"`);
  
  // Получаем контекстный код файла
  const contextCode = fileInfoResult.rows[0]?.context_code || 'DEFAULT';
  
  // Проверяем существование AI Item с таким full_name + context_code
  // Если существует - связываем с существующим
  // Если нет - создаем новый
}
```

### Поток данных

1. **Векторизация файла** → Специализированный сплиттер извлекает объекты
2. **Для каждого объекта с `full_name`**:
   - Создается или находится существующий `AI Item` (уникальность по `full_name` + `context_code`)
   - Сохраняется чанк **уровня L0 (0-исходник)** с исходным кодом
   - Чанк автоматически связывается с `AI Item` через `ai_item_id`

### Связь "Файл → AI Item"
- **Один ко многим**: Из одного файла создается **множество** AI Items
- Пример: файл `api.js` с 3 функциями → 3 отдельных AI Items
- Каждый AI Item представляет именованную логическую сущность (функция, класс, таблица, секция MD)

### Удаление и очистка

При удалении чанка уровня 0 автоматически удаляется запись из таблицы `ai_item`, если на нее больше нет ссылок.

## Генерация многоуровневых чанков

### Два режима работы

**1. Автоматический режим** (сервер выбирает промпты из `.env`):

```json
{
  "level": 1,  // или 2
  "model": "gpt-4"  // опционально
}
```

Логика:
- Определяет тип файла по расширению (`.js`, `.sql`, `.md`)
- Определяет тип объекта из `ai_item.type` (function, class, table, etc.)
- Нормализует типы для соответствия переменным `.env`
- Находит шаблоны: `{FILE_TYPE}_L{LEVEL}_{OBJECT_TYPE}_PROMPT` и `*_INPUT_TEXT`
- Пример: `JS_L1_FUNCTION_PROMPT`, `SQL_L2_TABLE_INPUT_TEXT`

**2. Ручной режим** (пользователь передает свои промпты):

```json
{
  "level": 1,
  "prompt": "Опиши связи этой функции",
  "inputText": "Какие функции она вызывает?"
}
```

### Процесс генерации

1. Получает AI Item и его L0 чанк (исходный код)
2. Удаляет существующие чанки указанного уровня (L1 или L2)
3. Вызывает внешний AI-сервис (`REQ_SERVER_URL`) или mock-функцию
4. Создает embedding для сгенерированного контента
5. Сохраняет новый чанк как дочерний к L0 чанку
6. Возвращает `promptInfo` с информацией о режиме и шаблонах

## Связи между объектами

### Важно: связи НЕ жесткие, а текстовые!

Связи между AI Items хранятся **не как граф в БД**, а как **текстовое описание** в чанках уровня L1.

**Пример:**

AI Item: `calculateTotal(orderId)`
- **L0 чанк:** Исходный код функции
- **L1 чанк:** "Функция вызывает `getOrderItems(orderId)` и `applyDiscount(price)`. Делает SELECT к таблице `products`."
- **L2 чанк:** "Вычисляет итоговую стоимость заказа с учетом скидок."

В L1 чанке упоминаются другие AI Items (`getOrderItems`, `applyDiscount`, `products`), но **нет прямых FK-ссылок**.

### Как используются связи

- **Семантический поиск:** Когда спрашиваешь "Что использует таблицу products?", RAG находит L1 чанк с упоминанием "products"
- **Контекст для LLM:** L1 чанки включаются в промпт для более глубокого понимания кода

## Преимущества и недостатки

### 🟢 Преимущества

1. **Структурированная навигация по коду**
   - Автоматическое выделение именованных объектов
   - Группировка по контекстам и типам
   - Связи между файлами и объектами

2. **Многоуровневая система анализа**
   - Исходники → Связи → Логика
   - Возможность создавать производные знания

3. **Semantic Search с контекстом**
   - Поиск по типам объектов
   - Фильтрация по уровням абстракции
   - Контекстная группировка

4. **UI для управления знаниями**
   - Просмотр AI Items и их чанков
   - Создание связей между объектами
   - Экспорт структурированных данных

### 🔴 Ограничения и проблемы

1. **Сложность архитектуры**
   ```javascript
   // Автоматическое создание AI Item при сохранении чанка
   if (level === '0-исходник' && full_name) {
     // Множество проверок и создание связей
     // Усложняет понимание и отладку
   }
   ```

2. **Ограниченная автоматизация**
   - Парсинг SQL/JS эвристический, не 100% точный
   - Требует ручного управления контекстами
   - Связи между объектами создаются полуавтоматически

3. **Проблемы масштабируемости**
   - При больших кодовых базах слишком много AI Items
   - Нет автоматической дедупликации
   - Сложность поддержания консистентности

4. **Недостаточная гибкость**
   - Жесткая привязка к структуре `full_name`+`context_code`
   - Ограниченные типы файлов (JS, SQL, MD)
   - Нет поддержки других языков программирования

5. **L1/L2 не генерируются автоматически**
   - При векторизации файла создаются только L0 чанки
   - Для генерации L1/L2 нужно вызывать отдельные API endpoints

### Практические проблемы

1. **Orphaned AI Items** — остаются после удаления чанков
2. **Дублирование объектов** при изменении контекста
3. **Сложность миграций** при изменении схемы
4. **Отсутствие версионирования** изменений в AI Items

## Практические рекомендации

### Рабочий процесс

**1. Векторизация проекта (автоматически создаются AI Items + L0):**

```bash
# Сканирование и векторизация всех файлов
POST /scan-folder
Body: { "path": "C:/my-project/src" }

# Или векторизация конкретных файлов
POST /vectorize
Body: { 
  "fileName": "api.js",
  "contextCode": "BACKEND",
  "params": { "includeComments": true }
}
```

**2. Получение списка AI Items:**

```bash
GET /ai-items?contextCode=BACKEND
```

**3. Генерация L1 и L2 для ключевых объектов:**

```javascript
// Автоматическая генерация с шаблонами из .env
for (const item of aiItems) {
  // L1 (связи)
  await fetch(`/api/ai/ai-item/${item.id}/generate-chunk`, {
    method: 'POST',
    body: JSON.stringify({ level: 1 })
  });
  
  // L2 (логика)
  await fetch(`/api/ai/ai-item/${item.id}/generate-chunk`, {
    method: 'POST',
    body: JSON.stringify({ level: 2 })
  });
}
```

**4. Использование в RAG:**

```bash
POST /ask
Body: {
  "question": "Как работает функция calculateTotal?",
  "contextCode": "BACKEND",
  "chunkLevel": null  # Ищет во всех уровнях (L0, L1, L2)
}
```

### Рекомендации по применению

- **Генерировать L1/L2 только для ключевых объектов** или по запросу пользователя
- **Использовать контекстные коды** для группировки связанных файлов
- **Периодически проводить очистку** неиспользуемых AI Items

## Ограничения системы

### 1. Стоимость генерации L1/L2

**Проблема:** Каждый вызов генерации L1/L2 - это запрос к платному AI API (OpenAI или другой LLM).

Для большого проекта (1000+ функций):
- 1000 × 2 (L1 + L2) = 2000 запросов к AI
- При средней цене ~$0.002 за запрос = ~$4 за полную генерацию

**Рекомендация:** Генерировать L1/L2 только для ключевых объектов или по запросу.

### 2. Тесты используют mock AI сервис

**Проблема:** В тестах используется функция `callAiService()`, которая возвращает фиксированные строки, а не реальные вызовы к OpenAI или `REQ_SERVER_URL`.

**Что проверяется:** Механика работы (API endpoints, сохранение в БД, связи)  
**Что НЕ проверяется:** Качество генерируемых AI описаний связей и логики

**Решение для production:**
- Указать реальный `REQ_SERVER_URL` в `.env`
- Убрать или заменить mock-функцию на реальный HTTP-вызов

### 3. Связи между AI Items - текстовые

**Проблема:** Невозможно построить граф зависимостей SQL-запросом типа:
```sql
SELECT * FROM ai_item WHERE depends_on = 'calculateTotal'
```

Связи существуют только в тексте L1 чанков.

**Альтернатива (не реализована):**
- Создать таблицу `ai_item_relations`
- При генерации L1 чанка парсить текст и извлекать упоминания других AI Items
- Сохранять как FK-связи для построения графа

## Заключение

**AI Item** — это амбициозная попытка создать структурированную систему знаний с автоматической категоризацией объектов. Идея интересная, но **реализация переусложнена**.

**Полезность**: высокая для небольших проектов с четкой структурой кода.

**Недостатки**: сложность архитектуры превышает практическую пользу для большинства случаев использования. Система требует значительных усилий на поддержание и понимание.

Проект демонстрирует интересный подход к **semantic code analysis**, но нуждается в упрощении и более автоматизированном управлении жизненным циклом объектов.

Для **производственного использования** рекомендуется:

1. Настроить реальный `REQ_SERVER_URL` с AI моделью
2. Подготовить качественные шаблоны промптов в `.env`
3. Создать скрипт массовой генерации L1/L2 для выбранных AI Items
4. Добавить тесты с реальными вызовами AI для проверки качества генерации
