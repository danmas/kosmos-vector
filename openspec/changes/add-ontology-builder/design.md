# Design: add-ontology-builder

## Context

Онтология уже загружается (`onto_loading` в Step1) и валидируется
(`GET /api/ontology/validate`), и используется в concept-first retrieval
(`POST /api/ontology/ask`, `routes/rag.js`). Отсутствует только **построение** черновика
понятий. Реальность живёт в `ai_item` + чанках + L1-связях после Step1/2, эмбеддинги —
после Step4. Резолв grounding-целей уже реализован (`resolveGroundingTarget` в
`ontoLoader.js`).

## Goals

- Полуавтомат: за один-два захода получить приемлемый черновик понятий с grounding.
- Опираться на **векторизованную реальность**, а не на голый AST.
- Не ломать инварианты: MD — источник истины, `verified` только вручную, петля
  перезагрузки понятий заново векторизует `concept:*`.
- Переиспользовать существующее: `ontoLoader`, `step4Vectorize`, `validateOntology`.

## Non-Goals

- Полная автогенерация онтологии без человека.
- Reasoner / иерархия классов понятий, исполняемые «Активности».
- Автопокрытие всех `ai_item` понятиями (coverage — сигнал, не цель).
- Новый слой хранения: пишем в существующие `concepts/*.md` и onto-таблицы.

## Key Decisions

### Размещение: Step 6, а не Step 3

Слоты 1–5 заняты (`pipelineConfigService.js`): 3 = `enrichment (L2)`, 5 = `indexing`.
Построитель зависит от результата Step4, поэтому идёт **после** векторизации →
новый `id: 6 ontology_builder`. Это исправляет исходную гипотезу «между 1 и 4»:
grounding нечем подкреплять до векторизации.

### Петля, а не линейный раннер

Построение — цикл `suggest → review → materialize → (Step1 onto) → (Step4 concept:*)
→ validate → refine`, а не однократный «run». Поэтому три эндпоинта (`suggest` без
записи, `materialize` пишет MD, `apply` замыкает петлю), а не один step-runner. Step 6
в ленте — точка входа в диалог, статус = сводка последнего прогона, шаг
перезапускаемый.

### suggest — read-only

`suggest` ничего не пишет (ни файлов, ни БД) — это черновик для правки человеком.
Запись только через `materialize`/`apply`. Так исключаем «тихий» мусор в git.

### Глубина авто — конфигурируемая

Параметр `depth`: `concepts` (только кандидаты понятий) или `concepts+grounding`
(понятия + grounding-кандидаты по эмбеддингам), default `concepts+grounding`. Полный
авто-написанный MD как отдельный режим — вне scope v1 (риск мусора; см. Open Questions).

### Источники кандидатов

- Понятия: кластеризация непокрытых `ai_item` по эмбеддингу + LLM-лейблинг; якоря —
  публичные API, центральные таблицы (входящая степень L1), high-fan модули, доменные
  термины из doc-чанков.
- Grounding: ближайшие `ai_item` по эмбеддингу + совпадение имени → `resolveGroundingTarget`
  (в обратную сторону) с confidence; при ≥2 равнозначных — помечаем неоднозначным.
- Отношения: подъём L1-связей между grounded-items до уровня понятий
  (`uses`/`part_of`/`precedes`).

## Risks / Trade-offs

- **Галлюцинации LLM** в понятиях/grounding → suggest read-only + обязательное ревью +
  `validate` перед `verified`; confidence и source у каждого grounding-кандидата.
- **Протухание эмбеддингов понятий** после правки MD → `apply` всегда повторно
  векторизует `concept:*` (иначе retrieval видит старое).
- **Стоимость LLM/эмбеддингов** на больших контекстах → `maxConcepts` и работа только по
  непокрытым/якорным items.
- **Кросс-репо изменение** (backend + UI) → спека держит оба capability; порядок влития:
  сначала backend-эндпоинты, потом UI.

## Migration / Rollout

1. Backend: определения (Step 6) + build-эндпоинты, без UI — проверяется curl-ом.
2. UI: диалог + карточка + apiClient.
3. Обкатка на пилоте `KOSMOS-VECTOR`, затем на втором домене (CARL) —
   `Ontology/ONTOLOGY_PLAN.md`, этап 5.
4. Обратная совместимость: контексты без onto_loading видят Step 6 как «нет папки
   понятий» с подсказкой настроить `onto_loading.dirs`.

## Open Questions

- Нужен ли режим «полный черновик MD» (level 3) сразу, или после обкатки level 2?
- Хранить ли историю прогонов построителя (как `pipeline/steps/history`) для дифов
  черновиков между заходами?
- Где именно писать `concepts/*.md`, если `onto_loading.dirs` содержит несколько путей —
  всегда первый, или спрашивать в UI?
